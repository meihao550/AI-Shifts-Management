# 従業員ごとの固定カレンダー（曜日パターン）を毎月流用する

木曜だけ出勤・他は休み、といった従業員は毎月同じ曜日パターンになる。毎月その休日を手入力するのは手間で、シフト作成時間を圧迫する。そこで**従業員ごとに曜日単位の固定カレンダー**（`出勤`/`休み`/`指定なし`）を持ち、生成時に対象月の日付へ**自動展開**する。深夜の曜日固定の人もこれで扱える。

- 保存単位は `EmployeeFixedSchedule(employee_id, day_of_week[月=0..日=6], status[work/off])`。行の無い曜日は「指定なし」。
- 生成時の展開: `休み(off)` → その月の該当日を `unavailable`（ハード休み）。`出勤(work)` → `preferred`（その日に入りやすくする**弱いnudge**）。
- **precedence**: 同じ (従業員, 日付) に個別の希望・不可・有給（concrete availability）がある場合はそちらを優先し、固定由来はスキップする。
- 編集は**別ルートの専用ページ** `/employees/:id/calendar`（従業員一覧の「カレンダー」から遷移、「戻る」で一覧へ）。

## Considered Options

- **固定「出勤」をハードな強制出勤にする**（却下）: 必要人数・連勤制限・保険時間と衝突してインフィージブルを招きやすい。当面は preferred の弱いnudgeに留め、必要なら後日ハード化する。
- **具体的な日付行を毎月コピーして持つ**（却下）: データが増え、テンプレとの二重管理になる。曜日パターンを1つ持ち生成時に展開する方が源泉が単一で扱いやすい。
- **月カレンダーUIで毎月編集**（却下）: 毎月の手間を無くすのが目的。曜日パターンの専用ページにする。

## Consequences

- DBに `employee_fixed_schedules` テーブルを追加。
- 既存の `_unavailable_lookup()`/`_preferred_lookup()`（`scheduler.py`）が展開結果の受け皿になり、スケジューラ本体は変更不要。展開はルーター（`shifts.py`）で行う。
- 「出勤」は強制ではないため、必要人数が無い日はその曜日でも入らないことがある。
