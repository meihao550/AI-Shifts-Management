# メインシフト区分(朝/夜/深夜)を廃止し、勤務可能時間帯(1時間窓)に一本化する

従業員をどのパターンに配置してよいかを制御する仕組みが、**メインシフト区分**（`main_shift_type` = 朝/夜/深夜 ＋ `main_shift_pinned` によるハード固定）と、後から追加した**勤務可能時間帯**（`available_start_hour`/`available_end_hour` の1時間単位ハード窓）の**2系統**存在し、二重管理になっていた。3区分は粒度が粗く、`main_shift_pinned` をデフォルトONにすると新規従業員が UI 既定の「朝」に固定され、夜・深夜へ一切入れられなくなる問題があった。1時間窓は「窓に完全に収まるパターンは全て配置可」で必要十分に表現でき、区分を包含する。よって**メインシフト区分を廃止し、配置制御を勤務可能時間帯に一本化する**。

- **scheduler 側の区分ロジック**（ピン留めハード制約・メイン寄せの弱ボーナス）は、削除ではなく**コメントアウトし廃止理由を明記**する。挙動の由来を追えるようにするため。
- **UI からは区分入力を削除**し、**DB マイグレーションで `main_shift_type` / `main_shift_pinned` カラムを除去**する。
- 新規従業員の勤務可能時間帯は**未設定(=無制限)**を既定とし、一律のデフォルト窓は置かない（窓は本来その人固有の稼働可能時間のため）。既存従業員は変更しない。

## Considered Options

- **区分と窓を併存させる**（却下）: 「どのパターンに入れるか」を2系統が同時に制御し、矛盾・二重管理・UIの混乱を招く。区分が持てる情報は窓で表現できる。
- **区分を残し、窓に合わせて意味を「優先帯（ソフト寄せ）」に再定義**（却下）: 現状の弱ボーナス(weight=1)は効果が薄く、窓があれば固定の必要もない。語彙を増やすだけで実益が乏しい。

## Consequences

- `メインシフト` という語彙は「勤務可能時間帯」に統合される（`CONTEXT.md` を更新）。
- 区分に依存していたコード・テスト・API/型を窓ベースへ寄せる必要がある。
