# ログインを許可リスト制にする（誰でも→許可された人だけ）

デプロイに向けてログインを厳格化する。従来は Google OAuth で認証できれば誰でも（または `allowed_google_domain` 一致で）自動的にユーザー作成・ログインでき、初回ログイン者が自動で管理者になっていた。これを **許可リスト（`allowed_logins`: 氏名・メール・権限）に登録された email だけログインできる** 方式に変更する。

- ログイン時に email を `allowed_logins` と照合（大文字小文字無視）。無ければログイン不可。
- **権限(role)の真実源は許可リスト**。ログインの度に `User.role` を許可リストの role へ同期する。
- 許可リストは**管理者専用画面**（`/login-users` → `/api/allowed-logins` CRUD）で管理。初期管理者として **`ziyin550@gmail.com`** をマイグレーションで seed。
- 開発用ログイン（フロントの「開発用」ブロックと `/api/auth/dev-login`）は**削除**。
- OAuth コールバックで許可外だった場合は 403 JSON ではなく `/login?error=not_allowed` へリダイレクトし、画面で理由を表示する。
- 最後の管理者を削除できないガードを入れる（ログイン不能事故の防止）。

## Considered Options

- **`allowed_google_domain` によるドメイン制限のみ**（却下）: 許可したいのは個別のメール（`gmail.com` の個人アカウント含む）で、ドメイン単位では表現できない。ドメイン設定は任意で残置。
- **User テーブルを事前作成して制御**（却下）: User は OAuth 時に作られる実体。「ログインを許可する人」の管理は別概念として `allowed_logins` に分けた方が明確。
- **role を許可リストに持たせない（全員 employee、管理者は初回のみ）**（却下）: 管理者を後から増やせない。許可リストに role を持たせ真実源にした。

## Consequences

- 新テーブル `allowed_logins`（`user_role` enum を再利用）。
- 既存 DB に残る旧 User（dev 作成分）は、許可リストに無ければ今後 OAuth ログイン不可。本番は新規 DB で seed される。
- 権限変更は次回ログインで反映される（即時ではない）。
